# Data model

The database is PostgreSQL in deployment, with SQLite supported for local tests. Every schema
change goes through Alembic (`backend/app/db/migrations`). Common conventions:

- Primary keys are UUIDs (`id`), generated by the application.
- Timestamps are `timestamptz` in UTC, in `created_at` / `updated_at`.
- Structured fields use `JSONB` on PostgreSQL and `JSON` on SQLite.
- Constraint and index names are deterministic (`pk_<table>`, `ix_<table>_<col>`, `fk_…`).
- Missing values are `NULL`, never `0`.
- Secrets are never stored in normal columns. Endpoints hold a `secret_reference`, such as the
  name of an environment variable, and never the key itself.

(`ImmutableRecordError`). Changing data means uploading a new version.

### `benchmark_runs` (migration `0004`)

`project_id` (cascade), `profile_id` (reserved for M4 profiles), `name`, `description`, `status`
(indexed; see the run state machine in the CHANGELOG, Milestone 3), `configuration_snapshot` (jsonb, immutable and
secret-free), `framework_version`, `created_by`, `started_at`, `completed_at`,
`cancel_requested_at`, `error_summary`, `progress` (jsonb, written by the worker), `pass_count`,
`retry_failed_requested`, `worker_id`, and `lease_expires_at`. The last two implement the
database-backed queue. A worker claims a run with a conditional `UPDATE` and renews the lease on
every flush; when a lease expires, another worker can take the run over.

### `run_datasets` (migration `0004`)

`run_id`, `position`, `dataset_version_id` (`SET NULL` if the dataset is deleted later),
`dataset_id`, `content_hash`, and `record_count`. The hash and count survive deletion, so a run
always records exactly what it ran on.

### `run_models` (migration `0004`)

`run_id`, `position`, `endpoint_id` (`SET NULL`), `endpoint_snapshot` (secret-free effective
configuration), `declared_model_metadata`, `hardware_metadata`, `status`, `progress`,
`started_at`, and `completed_at`.

### `run_case_results` (migration `0004`)

One row per **attempt**: `run_id`, `run_model_id`, `dataset_case_id` (`SET NULL`),
`case_identifier`, `sequence` (per-run cursor, unique; used as the SSE event id), `phase`
(`warmup` | `measured`), `request_index`, `attempt_number`, `pass_number` (increments on resume or
retry-failed), `load_step`, `is_final` (the attempt that decided the request), `is_warmup`,
`status`, `error_type`, `error_message`, `http_status`, `latency_ms`, `ttft_ms`,
`request_metadata`, `response_data`, and `performance_metrics`. The unique key is
(`run_model_id`, `phase`, `request_index`, `attempt_number`), so resuming can't duplicate work.

### `run_aggregate_metrics` (migration `0004`)

`run_id`, `run_model_id`, `load_step` (NULL means the whole run; ramp runs also get one row per
step), `metric_name`, `aggregation` (for example `p95`, `mean`, `value`, `ratio`),
`metric_value` (**nullable**: unavailable is never stored as 0), `metric_unit`, `sample_count`,
and `metadata` (definition, method, and the reason when unavailable).

### `evaluation_profiles` (migration `0005`)

`project_id` (nullable, `CASCADE`), `name` (unique), `description`, `suites`,
`evaluator_configuration`, `generation_configuration`, and `load_configuration` (JSON). A run
records the profile in its snapshot and in `benchmark_runs.profile_id`; it copies the settings,
so a profile can change or be deleted without affecting past runs.

### `evaluation_results` (migration `0005`)

One row per evaluator per evaluated attempt: `run_id`, `run_model_id`, `run_case_result_id`
(all `CASCADE`), `suite`, `evaluator_name`, `evaluator_version`, `status` (`completed`,
`failed`, `skipped`, `not_applicable`, `requires_review`), `score` (**nullable**), `passed`
(nullable), `label`, `rationale`, `evidence` (JSON), and `metadata` (JSON). The unique key is
(`run_case_result_id`, `evaluator_name`); the index on (`run_id`, `evaluator_name`) serves the
results filters. Rows are written in the same transaction as their attempt. Quality aggregates
(`quality.*`, `tool.*`, `rag.*`, `hallucination.*`) go into `run_aggregate_metrics` like the
performance metrics.

Claim-based evaluators (M5) store one `evidence` entry per claim: `claim`, `classification`
(`supported`, `unsupported`, `contradicted`, `unverifiable`), `evidence` (excerpt), `passage`,
`document_id`, `chunk_id`, `source`, `page`, `supporting_passages`, `citations`, `rationale`,
`confidence` (judge only), `method`, `review_recommended`, and `review_status`. Their `metadata`
holds `claim_counts`, the extractor and verifier names and versions, the judge identity and
prompt version, and the abstention state. M5 adds no migration.

## Proposed (each table is added by the milestone that uses it)

| Table | Milestone | Key columns |
|---|---|---|
| `comparisons` | M6 | `project_id`, `name`, `run_ids` jsonb |
| `reports` | M6 | `run_id`, `report_type`, `storage_location`, `generated_at`, `report_metadata` |

Design notes:

- `is_warmup` and `phase` are added to `run_case_results` so that warm-up
  requests can be excluded from aggregates.
- `run_case_results` is keyed by request index rather than dataset case, because a run can send
  more requests than there are cases (cases repeat in order). `run_datasets`, `sequence`,
  `pass_number`, `is_final`, and the lease columns are additions that make runs resumable and
  streamable.
- Evaluation profiles moved to M4, where they carry evaluator configuration.
- M2 stores case content as jsonb in `dataset_cases` (`storage_location` is `NULL`), within
  the configured record limits. File-backed storage for very large datasets can be added later
  through `storage_location` without changing the hash definition.
